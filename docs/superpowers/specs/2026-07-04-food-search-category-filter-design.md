# 직접 등록 검색 — 카테고리 필터 칩 설계

**날짜:** 2026-07-04
**대상:** `/add` 페이지 식약처 검색 탐색성 개선

## 문제

직접 등록(`/add`) 페이지에서 키워드로 식약처 식품영양성분DB를 검색할 때,
수박·블루베리 같은 **원재료 과일/채소를 찾을 수 없다.** 사용자가 "더보기"를
여러 번 눌러도 도달하지 못한다.

### 근본 원인 (실제 API 검증 완료)

식약처 `FoodNtrCpntDbInfo02` API를 직접 호출해 확인:

- 식약처 DB는 **상용제품·외식(프랜차이즈) 메뉴가 절대다수**, 원재료(생것)는 극소수.
- API는 **관련도순이 아니라 DB 등록순**으로 결과를 반환 → 가공식품이 앞을 전부 채움.
  - `블루베리` 검색 → totalCount **2,427개**, 1~20위 전부 마카롱·머핀·베이글.
    진짜 `블루베리_생것`(43kcal)은 100위 밖.
  - `수박` 검색 → totalCount **428개**, 1~20위 전부 아이스크림·주스.
- 앱에 **100개 상한**(`MAX_TOTAL`/`MAX_RESULTS`, quota 보호용)이 있어,
  원재료가 100위 밖이면 **더보기를 아무리 눌러도 물리적으로 도달 불가**.
- 로컬 프리셋 `src/data/food-presets.json`은 **현재 0개(빈 배열)** — 검색이 100% API에 의존.

### 결정적 지렛대

API에 `FOOD_CAT1_NM` 카테고리 파라미터를 붙이면 원재료만 정확히 걸러진다:

- `수박 + FOOD_CAT1_NM=과일류` → **3개** (수박_적육질_생것 31kcal, 황육질_생것, 애플수박)
- `블루베리 + FOOD_CAT1_NM=과일류` → **3개** (생것 43 / 말린것 325 / 얼린것 41)

## 목표 / 비목표

**목표**
- 검색 결과 위에 카테고리 필터 칩을 두어, 한 번의 탭으로 원재료 위주 결과를 얻는다.
- 기존 검색 동작(가공식품 탐색)을 깨지 않는다.

**비목표**
- 프리셋 목록 채우기(별도 작업으로 분리 가능).
- 자동 재정렬/다중 병렬 쿼리(quota 부담으로 제외).
- 검색 관련도 랭킹 알고리즘 자체 개선.

## 설계

### UX / 동작

- 검색 모드(쿼리 1자 이상)에서만 검색창 아래에 칩 행을 노출. 쿼리가 비면 칩도 숨김.
- 칩은 가로 스크롤 단일 행.
- **기본 선택 = `전체`** — 필터 없음, 현행과 동일 동작(비파괴적).
- 칩 탭 → 해당 `FOOD_CAT1_NM`을 API 쿼리에 추가해 **1페이지부터 재검색**.
- 카테고리가 걸리면 결과가 대개 3~30개 → "더보기"가 거의 불필요해짐(부수 효과).
- 선택된 칩은 시각적으로 강조(채워진 배경), 나머지는 아웃라인.

### 칩 세트 (API 카테고리와 1:1 매핑 — 탭당 API 호출 1회)

| 칩 라벨 | `FOOD_CAT1_NM` 값 | 비고 |
|---|---|---|
| 전체 | (없음) | 기본값, 현행 동작 |
| 과일 | 과일류 | 검증 완료 |
| 채소 | 채소류 | 검증 완료 |
| 고기 | 육류 | 검증 완료 |
| 생선·해산물 | 어패류 | 검증 완료 |
| 유제품 | 우유류 | 검증 완료 |
| 곡류·밥 | 곡류 | 검증 완료 |
| 음료 | 음료 및 차류 | 검증 완료 |

> 참고: 일부 원재료는 naming 엣지케이스가 있음(예: 계란은 '난류'에서 0건 → '달걀',
> 두부는 가공식품). 이 경우에도 `전체` 칩이 fallback이므로 검색 자체는 막히지 않는다.
> 칩은 탐색을 **돕는** 보조 수단이지, 유일한 경로가 아니다.

### 데이터 흐름

```
add.tsx (selectedCategory state)
   └─ useFoodSearch(query, category)
        └─ searchFood({ q, pageNo, category })
             └─ FOOD_NM_KR=q [+ FOOD_CAT1_NM=category] → 식약처 API
```

## 기술 변경 (파일 3개, 옵셔널 추가분 — 비파괴적)

### 1. `src/lib/food-search.ts`
- `searchFood` inputValidator에 `category?: string` 추가.
- 값이 있으면 `url.searchParams.set("FOOD_CAT1_NM", category)`.
- 없으면 현행과 동일(파라미터 미설정).

### 2. `src/hooks/use-food-search.ts`
- 시그니처를 `useFoodSearch(query, category?)`로 확장.
- **캐시 키에 category 포함**: `food_search_cache_v4_{q}__{cat}__p{n}`.
  스키마 변경이므로 `CACHE_PREFIX`를 `v3` → `v4`로 bump(기존 캐시 자동 무효화).
- category가 바뀌면 query 변경과 동일하게 1페이지부터 리셋 후 재fetch.
- 첫 페이지 fetch useEffect의 의존성에 `category` 추가.
- `searchFood` 호출에 `category` 전달(page1 및 loadMore 양쪽).

### 3. `src/routes/add.tsx`
- `selectedCategory: string | null` state 추가(기본 `null` = 전체).
- 칩 라벨→FOOD_CAT1_NM 매핑 상수(`SEARCH_CATEGORY_CHIPS`) 정의.
- 검색 모드(`inSearch`)에서 검색 결과 섹션 위에 칩 행 렌더.
- `useFoodSearch(query, selectedCategory ?? undefined)`로 연결.
- 쿼리가 비면(`!inSearch`) `selectedCategory`를 `null`로 리셋(선택 유지 여부는 구현 시 결정 — 기본은 리셋).

## 엣지 케이스 & 에러 처리

- 카테고리 필터 결과가 0건: 기존 "찾는 음식이 없나요? → 커스텀 등록" CTA가 그대로 안내.
- API 실패: 기존 `apiError` 처리 경로 재사용(칩과 무관).
- 캐시: (q, category, page) 3-튜플 키로 격리 — 카테고리 전환 시 서로 오염 없음.
- customMatches/presetMatches(로컬)는 카테고리 필터의 영향을 받지 않음
  (로컬은 API가 아니므로) — 현행 dedup 로직 유지. 프리셋이 비어 있어 실질 영향 미미.

## 테스트 / 검증

- 수동: `블루베리` 검색 → `과일` 칩 탭 → 생것/말린것/얼린것 3개 노출 확인.
- 수동: `전체` 칩에서 기존과 동일하게 가공식품 노출되는지(비파괴 확인).
- 캐시 격리: `블루베리`를 전체→과일→전체 전환 시 각기 올바른 결과.
- 빈 쿼리 전환 시 칩/필터 리셋 확인.
